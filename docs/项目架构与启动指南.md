# 项目架构与启动指南

`football-team-stats` 是一个用于维护球队球员、赛季、比赛日和赛季统计的 Next.js 应用。本指南是从空机器启动、部署和维护的权威入口；所有示例中的账号、密码、令牌、主机名和仓库地址均为占位符，必须替换，不能复制到生产环境。

## 1. 架构与职责边界

```text
浏览器 UI
  -> Next.js 页面 / React 组件
  -> App Router API（Zod 校验）
  -> lib/server 服务、AI 解析器或确定性统计纯函数
  -> Prisma
  -> PostgreSQL
```

- `app/` 包含 App Router 页面与路由处理器。公开首页在 `app/page.tsx`；管理页在 `app/admin/page.tsx`、`app/players/`、`app/seasons/`、`app/matchdays/`、`app/rankings/`、`app/team-photos/`。
- `components/` 放可复用界面：`AppShell.tsx` 是后台布局，`MatchEntryForm.tsx` 负责比赛日录入，`PlayerBulkImport.tsx` 负责名单批量识别与导入。
- `app/api/**/route.ts` 是服务端边界。大多数 JSON API 先由 `lib/validations.ts` 的 Zod schema 校验，数据库异常统一通过 `lib/server/api-error.ts` 转成可读响应；登录接口和 `FormData` 图片上传则分别做账号字段、文件类型与大小的专门校验。
- `lib/ai/` 只负责把赛后文字变为待确认的结构化数据；`lib/server/confirm-matchday.ts` 负责确认后写入正式事件；`lib/stats/calculate.ts` 是无数据库依赖的统计纯函数；`lib/server/stats.ts` 负责从已确认事件读取并组装统计输入。
- `prisma/schema.prisma` 定义 PostgreSQL 数据模型，`prisma/migrations/` 是可部署的迁移历史。不要手改已在生产环境执行过的迁移。

### 核心数据关系

```text
Season 1 --- * MatchDay 1 --- * TeamAssignment --- 1 Player
                    |   \--- * InternalGame --- * GoalEvent
                    |   \--- * TeamMatchdayResult
                    |   \--- * PlayerMatchdayPoint --- 1 Player
                    |   \--- * Award --- 0..1 Player
                    |   \--- * MatchParseResult
Player 1 --- * PlayerAlias
Season 1 --- * PlayerStatAdjustment --- 1 Player
```

- `Player` 存标准名、状态、头像等；`PlayerAlias` 存昵称、错别字、简称和人工别名。标准名全局唯一，别名也全局唯一；别名不能与任何标准名冲突。
- `Season` 由 `startDate`、`endDate` 和状态定义，不把赛季长度写死。`MatchDay` 归属赛季，分 `INTERNAL` 与 `EXTERNAL`，保存原始文本和解析/确认状态。
- `TeamAssignment` 记录当天阵容、队色、守门员和队长。同一比赛日同一球员只能出现一次。队内赛使用红、蓝、白；队外赛使用 `EXTERNAL`。
- 队内赛以 `InternalGame` 保存每一节比分（同一比赛日的节次唯一）。`GoalEvent` 保存进球、助攻、数量和原文；队内赛可关联小节，队外赛不关联。
- `TeamMatchdayResult` 保存当天三队的积分、进失球、排名及是否需要人工判定；`PlayerMatchdayPoint` 保存队内基础/额外积分；`Award` 保存奖项；`PlayerStatAdjustment` 保存人工的赛季数据调整。`MatchParseResult` 留存每次 AI/本地解析结果与模型名。

## 2. 业务流程

### 解析、人工确认与正式入库

1. 管理员创建赛季、球员和比赛日，并录入当天阵容与赛后文本。
2. `POST /api/matchdays/:id/parse` 读取球员及其别名，调用 `lib/ai/deepseek.ts`，并用 `lib/ai/schemas.ts` 校验输出；原文、结构化 JSON、模型名和状态写入 `MatchParseResult`。
3. 确认页 `app/matchdays/[id]/confirm/page.tsx` 显示比分、进球、助攻、低置信度匹配和 `uncertainItems`。管理员必须补全未匹配球员，才能确认；也可将原文名保存为别名。
4. `POST /api/matchdays/:id/confirm` 调用 `confirmMatchDay`。事务会先删除该比赛日已有的正式进球、积分、队伍结果、奖项和小节；传入新阵容时同时替换阵容，然后重建正式数据并将状态标为 `CONFIRMED`。因此重新确认不会保留旧事件。
5. 队内赛按每节胜 3、平 1、负 0 计算队伍积分；依次用总积分、净胜球、相互战绩排序。无法打破的平局会标为 `needsManualReview`。当天各队出勤球员按名次获得 3/2/1 基础赛季积分，再合并额外积分。队外赛不产生队内赛积分。

### AI 与本地 fallback

DeepSeek Key 只在服务端通过 `DEEPSEEK_API_KEY` 读取，浏览器不会直接调用模型。模型输出非 JSON 或 schema 不通过时，服务会最多再尝试一次；未配置 Key、调用失败或重试失败时，转用 `lib/ai/local-parser.ts` 的规则解析器。若规则解析也无法形成安全结果，则返回带 `uncertainItems` 的空结果，交由人工在确认页处理。无论使用哪种解析器，AI 都不计算最终榜单。

### 统计重算

`loadSeasonStats` 只读取该赛季 `CONFIRMED` 的比赛日及其 `TeamAssignment`、`GoalEvent`、`PlayerMatchdayPoint`、`TeamMatchdayResult`、`Award`，再调用 `calculateSeasonPlayerStats`。之后才按时间顺序应用 `PlayerStatAdjustment`，并重新计算总进球、总助攻、总出勤与场均值。榜单 API 与页面由这些事件重算，不以页面缓存或 AI 结果作为统计来源。

## 3. 管理权限、Cookie 与公开边界

1. 首页的管理员登录提交到 `POST /api/admin/login`。
2. 服务端比对 `ADMIN_USERNAME`、`ADMIN_PASSWORD`，成功后写入名为 `football_admin_session` 的 httpOnly、`SameSite=Lax` Cookie，时长 8 小时。
3. `middleware.ts` 对管理页面和 `/api/**` 做拦截，读取 Cookie 并与 `ADMIN_SESSION_TOKEN`（未配置时由账号密码派生）比较。不匹配的页面请求会跳回首页；API 返回 401。
4. 比赛分享页、`/api/public/**`、公开照片读取和 `GET /api/uploads` 是例外。上传写入与管理接口仍需要管理员会话。

生产环境 Cookie 会设置 `Secure`，所以公网必须由 HTTPS 访问。若仅使用 HTTP，浏览器不会保存登录 Cookie，表现为登录成功后仍被跳回首页。

## 4. 上传与持久化

- 头像上传：`POST /api/uploads/player-avatar`，只接受 JPEG、PNG、WEBP、GIF，最大 5 MB。
- 球队照片上传：`POST /api/uploads/team-photo`，同样的文件类型，最大 8 MB。
- `UPLOAD_DIR` 已配置时，文件保存到该目录下的 `players/` 与 `team-photos/`；未配置时保存到 `<项目目录>/public/uploads/`。
- 展示 URL 是 `/uploads/...`，实际由 `GET /api/uploads?path=...` 做受限读取；服务仅接受上述两个子目录和允许的扩展名，阻止路径穿越。

生产环境务必把 `UPLOAD_DIR` 指向项目发布目录之外的持久磁盘，并让运行服务的用户拥有读写权限；部署新版本时不要删除此目录。

## 5. Windows：从空机器启动

### 5.1 安装前置软件

安装以下软件并重新打开 PowerShell：

- Git；确认 `git --version` 可执行。
- Node.js 20 或 22 LTS；确认 `node --version` 可执行。
- Corepack（随 Node.js 发布）；确认 `corepack --version` 可执行。
- PostgreSQL（含 `createdb`、`psql`）；确认服务已启动，并记住自行设置的管理员密码。

### 5.2 获取代码与数据库

以下命令中的尖括号是必须替换的占位符：

```powershell
git clone <REPOSITORY_URL> football-team-stats
Set-Location football-team-stats
corepack prepare pnpm@9.12.3 --activate
corepack pnpm install --frozen-lockfile

# 使用能创建数据库的 PostgreSQL 管理员执行；两条命令都会按提示输入相应密码
createuser -U <POSTGRES_ADMIN_USER> -h <POSTGRES_HOST> --pwprompt <APP_DB_USER>
createdb -U <POSTGRES_ADMIN_USER> -h <POSTGRES_HOST> --owner=<APP_DB_USER> football_team

Copy-Item .env.example .env
notepad .env
```

在 `.env` 中仅填写自己的值，示例格式如下（不要把真实值提交或发到聊天/工单）：

```dotenv
DATABASE_URL="postgresql://<DB_USER>:<DB_PASSWORD>@<DB_HOST>:5432/football_team?schema=public"
DEEPSEEK_API_KEY="<DEEPSEEK_API_KEY_OR_EMPTY>"
DEEPSEEK_MODEL="deepseek-v4-flash"
ADMIN_USERNAME="<ADMIN_USERNAME>"
ADMIN_PASSWORD="<ADMIN_PASSWORD>"
ADMIN_SESSION_TOKEN="<LONG_RANDOM_SESSION_TOKEN>"
UPLOAD_DIR=""
```

本地不配置 `DEEPSEEK_API_KEY` 也能启动，解析会使用本地规则 fallback；不要保留示例文件中的默认管理员凭据。默认的空 `UPLOAD_DIR` 会使用项目内 `public/uploads`，适合本地开发。

### 5.3 初始化、运行与验证

```powershell
corepack pnpm prisma:generate
corepack pnpm prisma migrate deploy
corepack pnpm dev
```

打开 `http://localhost:3000`。Windows 也可双击 `start.bat`：它会创建 `.env`、安装依赖、生成 Prisma Client、默认执行迁移并启动开发服务器。默认只绑定 `127.0.0.1:3000`；若需要改变监听地址/端口，可设置 `START_HOST`、`START_PORT`。

提交或部署前运行：

```powershell
corepack pnpm test
corepack pnpm build
```

## 6. Ubuntu + nginx 生产部署

以下示例以 Ubuntu、专用非 root 运行用户 `football`、应用目录 `/srv/football-team-stats` 和上传目录 `/var/lib/football-team-stats/uploads` 为例。域名、仓库和密码均需自行替换。

### 6.1 安装运行时、应用和数据库

以下命令提供一条可直接执行的 Ubuntu 安装路线：先用 apt 安装 Git、PostgreSQL、nginx 和 NodeSource 所需工具，再安装 Node.js 22 LTS（仓库要求的 Node.js 20/22 LTS 中的 22）。NodeSource 的 `22.x` 会保持在该主版本最新可用补丁，不在文档中钉死易过期的补丁号。

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl gnupg git postgresql nginx
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt-get install -y nodejs
sudo corepack enable
node --version
corepack --version
psql --version
```

随后创建运行用户、数据库和应用：

```bash
sudo useradd --system --create-home --shell /usr/sbin/nologin football
sudo install -d -o football -g football /srv/football-team-stats /var/lib/football-team-stats/uploads
sudo -u postgres createuser --pwprompt football_app
sudo -u postgres createdb --owner=football_app football_team

sudo -u football git clone <REPOSITORY_URL> /srv/football-team-stats
cd /srv/football-team-stats
sudo -u football corepack prepare pnpm@9.12.3 --activate
sudo -u football corepack pnpm install --frozen-lockfile
sudo -u football cp .env.example .env
sudo -u football editor .env
sudo chown football:football /srv/football-team-stats/.env
sudo chmod 600 /srv/football-team-stats/.env
```

把 `.env` 仅保存在服务器上，权限应仅授予 `football` 用户；将 `DATABASE_URL` 指向专用的最小权限数据库用户，设置强管理员账号/密码和随机会话令牌，并设定：

```dotenv
UPLOAD_DIR="/var/lib/football-team-stats/uploads"
```

不要将 `.env` 放到仓库、镜像层或 nginx 配置中。完成配置后，生成客户端、应用迁移并构建：

```bash
cd /srv/football-team-stats
sudo -u football corepack pnpm prisma:generate
sudo -u football corepack pnpm prisma migrate deploy
sudo -u football corepack pnpm build
```

`migrate deploy` 只应用仓库内已有迁移，适合生产；不要在生产服务器使用 `prisma migrate dev`。

### 6.2 systemd 常驻进程

创建 `/etc/systemd/system/football-team-stats.service`：

```ini
[Unit]
Description=Football Team Stats Next.js service
After=network.target postgresql.service
Wants=postgresql.service

[Service]
Type=simple
User=football
Group=football
WorkingDirectory=/srv/football-team-stats
Environment=NODE_ENV=production
Environment=PORT=3000
EnvironmentFile=/srv/football-team-stats/.env
ExecStart=/usr/bin/env corepack pnpm start
Restart=on-failure
RestartSec=5
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

实际 `corepack` 位置会因 Node 安装方式不同而不同；在启用服务前以 `sudo -u football sh -lc 'command -v corepack'` 核实。若其不在 systemd 的 `PATH` 中，将 `ExecStart` 改成该命令的绝对路径。启动并查看日志：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now football-team-stats
sudo systemctl status football-team-stats --no-pager
sudo journalctl -u football-team-stats -n 100 --no-pager
```

部署更新前先备份数据库。应用目录中的所有 Git、依赖、迁移和构建操作均以 `football` 用户执行，避免 root 创建文件导致该服务用户无法更新；只有服务重启使用 `sudo`：

```bash
cd /srv/football-team-stats
sudo -u football git pull --ff-only
sudo -u football corepack pnpm install --frozen-lockfile
sudo -u football corepack pnpm prisma migrate deploy
sudo -u football corepack pnpm build
sudo systemctl restart football-team-stats
```

保持 `UPLOAD_DIR` 不变。

### 6.3 nginx、HTTPS 与反向代理

先准备有效 TLS 证书，再将以下站点配置保存为 `/etc/nginx/sites-available/football-team-stats`（将 `football.example.com` 替换为真实域名；证书路径也按实际签发工具替换）：

```nginx
server {
    listen 80;
    server_name football.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name football.example.com;

    ssl_certificate     /etc/letsencrypt/live/football.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/football.example.com/privkey.pem;

    client_max_body_size 10m;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}
```

验证并重载：

```bash
sudo ln -s /etc/nginx/sites-available/football-team-stats /etc/nginx/sites-enabled/football-team-stats
sudo nginx -t
sudo systemctl reload nginx
```

必须让 HTTP 统一跳 HTTPS，并保留 `Host` 与 `X-Forwarded-Proto`。生产 Cookie 带 `Secure` 标记：证书失效、用户通过 HTTP 访问，或代理没有正确服务 HTTPS 时，后台会出现登录循环。上传上限 8 MB，nginx 的 `client_max_body_size` 至少应为 10 MB。

## 7. 迁移、维护与常见故障

### 例行命令

```bash
corepack pnpm test
corepack pnpm build
corepack pnpm prisma:generate
corepack pnpm prisma migrate deploy
```

本地新建迁移才使用 `corepack pnpm prisma:migrate`（即 `prisma migrate dev`）；生产只使用 `prisma migrate deploy`。更新前备份数据库；执行后用 `pnpm test` 和 `pnpm build` 验证代码，再检查服务日志与首页/后台登录。

### 故障排查

| 现象 | 检查与处理 |
| --- | --- |
| 数据库认证或连接失败（P1000/P1001） | 确认 PostgreSQL 正在运行、`DATABASE_URL` 的主机/端口可达、用户名密码正确，并检查防火墙和数据库监听地址。不要把连接串贴到日志或工单。 |
| 数据库不存在（P1003） | 以数据库管理员创建 `football_team`，确认连接串中的数据库名一致，然后运行 `corepack pnpm prisma migrate deploy`。 |
| 表不存在（P2021） | 在确认连接到正确数据库后运行 `corepack pnpm prisma migrate deploy`，再重启应用。 |
| Corepack/pnpm 出现 EPERM 或权限问题 | 关闭正在占用项目、`node_modules` 或 pnpm store 的编辑器/终端；在当前用户下重新打开 PowerShell/终端，再执行 `corepack prepare pnpm@9.12.3 --activate` 与安装命令。避免以管理员和普通用户混用同一个依赖目录。 |
| 未配置 DeepSeek Key 或调用失败 | 这是预期降级路径：系统使用本地规则解析器并标记需要复核。检查确认页的 `uncertainItems`，人工补全后再确认入库。 |
| 图片上传失败或重启后丢失 | 检查 `UPLOAD_DIR` 是否为持久目录、`football` 用户是否对其有读写权限、nginx 是否允许至少 10 MB 请求体。不要使用临时容器文件系统。 |
| 提示登录成功却返回首页 | 在 HTTPS 下重试；检查浏览器是否保存 `football_admin_session`，再检查 `ADMIN_SESSION_TOKEN` 是否稳定、nginx TLS/反代是否正常。生产环境不能通过纯 HTTP 登录。 |
| 迁移在身份完整性预检查处失败 | 先备份数据库，按报错清理重复标准名、重复别名，或“标准名与别名相同”的冲突后重试。不要删除/改写已部署迁移记录，也不要在不理解影响时直接删球员或别名。 |
| 迁移历史与数据库不一致 | 停止继续部署，先备份并比对 `prisma/migrations/`、`_prisma_migrations` 与实际 schema；由维护者决定是补迁移还是使用 Prisma resolve 标记历史。不要用 `migrate reset` 操作生产库。 |

## 8. 代码地图与 API 入口

- 页面：`app/page.tsx`（公开首页）、`app/admin/page.tsx`（后台）、`app/players/`、`app/seasons/`、`app/matchdays/internal/`、`app/matchdays/external/`、`app/matchdays/[id]/confirm/`、`app/matchdays/[id]/share/`、`app/rankings/`、`app/team-photos/`。
- 球员 API：`/api/players`、`/api/players/:id`、`POST /api/players/:id/aliases`、`DELETE /api/players/:id/aliases/:aliasId`、`/api/players/:id/stat-adjustments`、`/api/players/bulk`、`/api/players/parse`。
- 赛季与比赛 API：`/api/seasons`、`/api/seasons/:id`、`/api/matchdays`、`/api/matchdays/:id`、`POST /api/matchdays/:id/parse`、`POST /api/matchdays/:id/confirm`。
- 统计与公开 API：`/api/stats/season/:seasonId`、`/players`、`/player/:playerId`、`/rankings`（后三项均在同一 season 路径下），以及 `/api/public/overview`、`/api/public/matchdays/:id`。
- 照片与上传 API：`/api/team-photos`、`/api/team-photos/:id`、`POST /api/uploads/player-avatar`、`POST /api/uploads/team-photo`、`GET /api/uploads?path=players/<filename>`。

详细 API 请求字段以 `lib/validations.ts`、对应路由和前端调用为准；不应将管理 Cookie 或数据库凭据作为 API 参数传递。
