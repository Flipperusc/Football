# 球员姓名与别名完整性功能设计

## 目标

本次改动完成三个交付项：

1. 球员管理页支持删除已经保存的别名。
2. 球员标准姓名与全队所有姓名、别名共享唯一名称空间，冲突时返回明确的 `409 Conflict`。
3. 输出覆盖系统架构、核心数据流、Windows 从零启动和 Ubuntu 生产部署的项目文档。

## 名称唯一性规则

- 所有活跃和停用球员都参与名称冲突检查。
- 输入继续使用现有 Zod schema 的 `trim()` 行为，因此 `"张三"` 与 `" 张三 "` 视为相同名称。
- 名称按 PostgreSQL 当前字符串比较规则进行精确、区分大小写的比较，不额外做英文大小写或 Unicode 归一化。
- 两名不同球员不能拥有相同的标准姓名。
- 两名不同球员不能拥有相同的别名。
- 一名球员的标准姓名不能与另一名球员的别名相同。
- 同一球员也不能新增一个与自己的标准姓名完全相同的别名，因为该别名没有识别价值。
- 停用球员仍保留其标准姓名和别名；需要重新使用该身份时应恢复原球员，而不是新增同名球员。

## 数据库设计

保留现有 `Player` 和 `PlayerAlias` 模型，不引入新的名称注册表。

- 为 `Player.name` 添加 Prisma `@unique`，由数据库唯一索引保证标准姓名表内唯一。
- 将 `PlayerAlias` 的 `@@unique([playerId, alias])` 改为 `alias @unique`，由数据库唯一索引保证别名表内唯一。
- 在 Prisma SQL migration 中加入 PostgreSQL 触发器函数，检查 `Player.name` 与 `PlayerAlias.alias` 之间的跨表冲突。
- 触发器在新增或更新标准姓名、别名前取得由名称计算出的事务级 advisory lock，再执行跨表检查，避免两个并发事务分别写入不同表而绕过校验。
- 数据库触发器以 `unique_violation` 拒绝冲突，作为应用层预检查之外的最终一致性保护。
- migration 在创建唯一索引和触发器之前执行冲突检查；如果现有数据已重复或跨表冲突，迁移明确失败，不自动删除、合并或改名。

## 服务端设计

新增一个聚焦名称冲突的服务端模块，统一完成查询、错误类型和用户提示，避免在多个 route 中复制判断逻辑。

该模块覆盖以下写入路径：

- `POST /api/players`：单个新增球员。
- `PATCH /api/players/:id`：修改球员标准姓名。
- `POST /api/players/bulk`：批量导入，检查数据库现有名称以及批次内部冲突。
- `POST /api/players/:id/aliases`：新增别名。
- 比赛确认入库的 `saveAliases`：保存 AI 原文名称为别名。

API 在写入前做友好预检查，并把数据库竞争条件下的唯一约束异常统一转换为 `409 Conflict`。响应采用稳定 JSON 结构：

```json
{
  "message": "球员“张三”已存在",
  "code": "PLAYER_NAME_CONFLICT",
  "value": "张三"
}
```

根据冲突来源使用明确文案，例如：

- `球员“张三”已存在`
- `“小张”已被其他球员用作别名`
- `“张三”已是其他球员的标准姓名`
- `别名不能与球员姓名相同`

## 删除别名

新增接口：

```text
DELETE /api/players/:playerId/aliases/:aliasId
```

接口按 `id = aliasId` 和 `playerId = playerId` 同时定位记录：

- 找到时删除并返回 `204 No Content`。
- 记录不存在或不属于路径中的球员时返回 `404 Not Found`。
- 删除别名不修改历史比赛事件；历史事件引用的是 `Player.id`，别名只影响未来的名称识别。

球员管理页将别名显示为可关闭的 Ant Design `Tag`：

- 点击关闭按钮时阻止 Tag 立即消失，先显示 `Popconfirm` 二次确认。
- 确认后调用删除接口。
- 成功后刷新球员列表并显示“已删除别名”。
- 失败时保留标签，由现有请求错误处理展示服务端信息。
- 删除入口只放在球员管理页；球员详情页继续只读展示，避免重复维护入口。

## 测试策略

遵循 Red-Green-Refactor：先编写并运行会因功能缺失而失败的测试，再实现最小代码。

名称完整性测试覆盖：

- 新增与现有活跃球员同名时冲突。
- 新增与现有停用球员同名时冲突。
- 输入首尾空格后与现有名称相同时冲突。
- 标准姓名与其他球员别名冲突。
- 别名与其他球员标准姓名冲突。
- 别名与其他球员别名冲突。
- 同一批量导入内部的姓名或别名冲突。
- 数据库唯一约束异常能转换成稳定的 `409` 响应。

删除别名测试覆盖：

- 所属球员可以删除别名。
- 不能通过另一个球员的路径删除该别名。
- 不存在的别名返回 `404`。

完成后运行完整的 `pnpm test` 和 `pnpm build`；若本地 PostgreSQL 可用，再执行 migration 验证。

## 非目标

- 不自动合并已有的重复球员或冲突别名。
- 不改变球员历史比赛数据或统计规则。
- 不提供删除球员功能。
- 不做模糊、拼音、英文大小写或 Unicode 等价名称的唯一性判断。
- 不在球员详情页或比赛确认页增加删除现有别名的入口。

## 验收标准

- 管理员可在球员管理页经二次确认删除任一已保存别名。
- 无法通过伪造其他球员 ID 的请求删除该别名。
- 任何写入路径都不能让不同球员共享相同标准姓名或别名。
- API 对可预期的名称冲突返回 `409` 和清晰中文信息，而不是 Prisma 原始异常。
- 停用球员的名称仍会阻止重复创建。
- 项目文档可供一名没有仓库背景的开发者理解系统，并从空白 Windows 环境完成本地启动。
- 完整测试与生产构建通过。
