# PRD：试训球员、乌龙球独立统计与比赛日积分资格

日期：2026-10-21  
状态：用户已确认并要求直接实施（2026-10-21）；本地实现与验收已完成。  
适用范围：队内赛。基于当前 main 的代打／乌龙二次确认功能扩展。

## 最新修订（2026-10-21）

用户已要求撤销 US-006 的积分资格功能，所有正式球员正常计分；以下涉及取消／恢复积分的原需求不再生效。普通进球移除事件类型列，奖项与额外加分合并为“特殊积分与奖项”，移除附带积分与计分状态列，保存新别名移至试训球员上方。

## 1. 概述

现有系统要求进球参与者匹配正式球员，无法完整记录不属于固定队伍的试训人员；乌龙球虽然已不计普通进球和助攻，但仍与普通进球混在同一录入表中，也没有独立个人统计；现有阵容球员默认获得当天原队排名积分，无法按迟到、缺席或受伤情况取消个人积分资格。

本次增加独立试训区域、独立乌龙球区域，以及按比赛日控制的个人积分开关。团队比分、单节积分和最终排名继续根据实际比赛结果计算。

### 已确认的业务口径

- 试训区域只展示姓名，以及进球／助攻／乌龙对应的节次；仅供核对比赛，不进入正式球员赛季统计和榜单。
- 试训球员不绑定当天固定队伍，可以在不同小节代表不同队伍；得分归具体事件的受益队。
- 正式球员与试训球员配合进球时，正式球员的进球或助攻正常统计，试训球员不获得正式个人统计。
- 分队识别未成功的名字默认归入“试训待确认”，必须提醒管理员核对身份。
- 乌龙球单独录入与展示，无助攻；正式球员个人数据增加独立乌龙球数，不并入普通进球。
- 管理员可以取消正式球员某个比赛日的全部个人积分，包括原队排名基础积分和额外加分。
- 积分开关作用于整场比赛日，不按缺席小节折算；可恢复计分。

### 沿用规则与明确假设

- 沿用：未取消积分资格时，名单中的临时未到场者仍按原队排名计分；代打者的积分仍归当天原队，出勤不重复。
- 沿用：取消个人积分资格不移除阵容记录，不取消当天出勤，不清除真实发生的进球、助攻或乌龙。
- [Assumption] 试训身份仅用于该比赛日，不自动创建正式球员档案，不产生正式出勤或个人奖项积分，不跨比赛日按姓名自动合并。
- [Assumption] 本次仅扩展队内赛；试训区默认位于后台录入／确认页面，公开战报保留必要事件署名和“试训”标记，不新增公开试训榜单。
- [Assumption] “全部个人积分”指该比赛日产生的积分，不改动其他比赛日积分或独立的赛季人工调整记录。

## 2. 目标

- 管理员无需创建虚假的正式球员，即可保存含试训进球、助攻或乌龙的队内赛。
- 每个未识别身份均有明确待确认状态，不能静默排除正式球员统计。
- 试训事件正常影响团队比分、单节胜平负积分、净胜球和最终排名。
- 普通进球与乌龙在录入、比赛记录和个人数据中可分别核对。
- 取消积分资格后，该球员本比赛日基础积分、额外积分和总积分均为 0。
- 重新确认、恢复计分和身份纠正后，统计可从正式数据库记录重算，无重复累计。

## 3. 用户故事与验收标准

### US-001：识别并确认试训身份

**描述：**作为录入员，我希望未识别名字自动进入试训待确认区域，以便保留原始名单并纠正身份。

**验收标准：**
- [ ] 文本分队与图片分队解析均保留未匹配名字，默认进入“试训待确认”，展示待确认人数和原始名字。
- [ ] 管理员可逐项确认试训身份、重新匹配正式球员，或移除误识别内容；支持手工新增试训名字。
- [ ] 低置信度候选仍须人工复核，不能仅凭模糊候选自动记入某名正式球员。
- [ ] 未处理的身份阻止确认入库，并定位到相应条目；允许保留草稿。
- [ ] 纠正为正式球员后，恢复正式身份校验；若缺少当天原队，要求补选，不能擅自指定。
- [ ] 同一名字重复出现时提供合并／区分提示，不把已确认的正式球员重复建立为试训人员。
- [ ] 类型检查通过；在浏览器验证新增、纠正、移除和待确认提示。

### US-002：试训区域与比赛事件关联

**描述：**作为录入员，我希望在独立区域查看试训球员的事件节次，以便核对比赛记录。

**验收标准：**
- [ ] 独立区域标题为“试训球员”，业务数据列仅为“姓名、进球节次、助攻节次、乌龙节次”；身份确认状态与操作按钮不作为统计指标。
- [ ] 无事件的列显示“—”；同节多次事件以“第 2 节 ×2”等形式表达，不显示赛季累计数据。
- [ ] 该区域不增加固定队伍、出场小节、个人积分、出勤或个人数据总计列。
- [ ] 进球／助攻事件可选择已确认试训人员；每条事件仍须有实际小节与得分队，球队归属在事件表编辑。
- [ ] 同一试训人员第 1 节为蓝队进球、第 3 节为红队进球时，两条记录可同时保存，试训身份无固定队伍约束。
- [ ] 试训区域由事件记录生成，修改事件后相应节次同步更新，不单独维护第二份统计。
- [ ] 类型检查通过；在浏览器验证空记录、同节多次事件及跨节代表不同队伍。

### US-003：试训事件入库与团队／正式球员统计

**描述：**作为管理员，我希望试训事件影响团队比赛结果，同时保留正式球员应得的数据。

**验收标准：**
- [ ] 试训人员为蓝队打入唯一进球、该节蓝队 1:0 获胜时，蓝队获得 3 个单节积分，红队获得 0 分，净胜球与排名使用该比分。
- [ ] 上述进球只计一次；不能在已有比分上再追加一次试训进球。
- [ ] 正式球员张三助攻试训人员进球：张三助攻 +1；试训人员不进入正式进球统计。
- [ ] 试训人员助攻张三进球：张三进球 +1；试训人员不进入正式助攻统计。
- [ ] 试训人员不进入正式球员列表、赛季榜单、个人积分或正式出勤统计。
- [ ] 试训乌龙仅计受益队比分，保留该试训人员的乌龙节次；不产生正式球员个人乌龙数据。
- [ ] 无受益队、无有效小节、事件进球数量超过该队比分等输入须返回明确错误。
- [ ] 不放宽对未确认身份的限制；以专门试训身份支持事件保存，不用虚构正式球员 ID 绕过校验。
- [ ] 相关统计测试及类型检查通过。

### US-004：乌龙球独立录入与展示

**描述：**作为录入员，我希望乌龙球在独立表格录入，避免与普通进球或助攻混淆。

**验收标准：**
- [ ] 确认页面分别提供“普通进球”和“乌龙球”区域及新增按钮。
- [ ] 乌龙表包括节次、受益队、乌龙球员和数量；不提供助攻列或助攻输入框。
- [ ] 普通进球转换为乌龙时提示清除助攻；确认转换才移入乌龙区，取消则保留原记录。
- [ ] 乌龙转换为普通进球时，不恢复此前已清除的助攻，须重新选择。
- [ ] 绕过界面提交带助攻的乌龙时，后端拒绝保存并返回可读错误。
- [ ] 乌龙仍参加现有二次确认；可与代打身份同时发生，受益队校验遵循实际代表队关系。
- [ ] 比赛战报与分享／导出内容把普通进球与乌龙分列，团队总比分同时包含二者。
- [ ] 类型检查通过；在浏览器验证分区、转换、取消转换及无助攻输入。

### US-005：正式球员个人乌龙球数据

**描述：**作为管理员和查看数据的用户，我希望能够单独查看正式球员的乌龙球数。

**验收标准：**
- [ ] 球员详情的队内赛季数据增加“乌龙球”项，比赛记录提供各比赛日乌龙数量与对应节次。
- [ ] 球员发生 2 个普通进球和 1 个乌龙时，展示普通进球 2、乌龙 1，助攻仅来自普通进球事件。
- [ ] 乌龙不减少普通进球，不改变射手榜的进球数或进球场均计算，不新增乌龙排名榜。
- [ ] 代打时发生乌龙，乌龙数记实际发生乌龙的正式球员，比分记受益队。
- [ ] 已存在且明确标记为 OWN_GOAL 的历史事件参与重算；普通历史进球不得根据名字或文本猜测为乌龙。
- [ ] 试训身份事件不计入任何正式球员乌龙统计。
- [ ] 类型检查及统计测试通过；在浏览器核对个人数据和比赛记录。

### US-006：按比赛日取消／恢复全部个人积分

**描述：**作为管理员，我希望按缺席或受伤情况取消指定球员当天积分，并能撤销该选择。

**验收标准：**
- [ ] 确认页为当天正式球员提供“本场不计个人积分”操作；标记后显示“本场不计分”并提供恢复操作。
- [ ] 取消计分的确认说明明确包含基础积分和全部额外加分，不影响团队结果、出勤及真实进球／助攻／乌龙记录。
- [ ] 取消弹窗时不改变该球员资格；编辑资格后，正式数据仅在确认入库成功时更新。
- [ ] 原队第一名基础积分 3、额外加分 2 的球员，被标记后该比赛日基础积分、额外积分、总积分均为 0。
- [ ] 手工额外加分、解析出的额外加分以及奖项附带积分都不能绕过取消计分标记；原始条目保留并提示“本场不生效”。
- [ ] 恢复计分并重新入库后，依据当前原队排名和保留的额外加分重新计算；上例恢复为 5 分，而非累计为 10 分。
- [ ] 标记仅针对选中球员与当前比赛日，不能自动取消代打者、其他队员或其他比赛日的积分。
- [ ] 代打者继续按当天原队计算积分；管理端对谁点取消，就只取消谁的积分，无须建立强制一对一替补关系。
- [ ] 不改变团队排名、其他队员分配或奖项次数；影响依赖个人积分的榜单与场均积分。
- [ ] 类型检查及统计测试通过；在浏览器验证取消、恢复和额外加分失效提示。

### US-007：重新打开、身份纠正与确认一致性

**描述：**作为管理员，我希望重新编辑比赛时保留身份和计分设置，所有结果在确认后保持一致。

**验收标准：**
- [ ] 保存并重新打开后，试训身份、关联事件、乌龙分区及不计分标记均能还原。
- [ ] 修改参与者身份、事件类型、小节、得分队、数量或积分资格后，相关旧二次确认失效。
- [ ] 入库确认摘要明确列出试训身份与本场不计分球员，沿用现有代打／乌龙二次确认流程，避免连续弹出重复确认框。
- [ ] 重新解析不能静默覆盖已人工确认的身份或积分资格；出现冲突时要求复核，保留原人工设置用于核对。
- [ ] 试训人员纠正为正式球员并重新确认后，关联事件归入正确个人统计，试训区域不留下重复记录。
- [ ] 删除、转换或更正事件后，重新入库替换旧正式记录，不累计旧统计；取消或事务失败则保留此前正式数据。
- [ ] 历史比赛缺少新增积分资格字段时，默认正常计分；不批量取消历史球员资格。
- [ ] 类型检查通过；在浏览器验证重开、纠正、确认失效与取消操作。

### US-008：完整流程自动化端到端测试

**描述：**作为测试人员，我希望通过自动化测试覆盖从分队识别到正式统计的完整过程，防止跨页面和数据层回归。

**依赖：**US-001 至 US-007。

**验收标准：**
- [ ] 自动化测试从分队解析产生未匹配名字开始，确认试训身份，录入跨节试训事件和正式球员配合，完成入库后验证数据库、团队结果及页面展示。
- [ ] 测试录入正式球员乌龙与试训乌龙，验证独立展示、无助攻、普通进球不变，以及正式个人乌龙数只包含本人事件。
- [ ] 测试给基础积分 3、额外加分 2 的正式球员取消积分，验证其个人积分为 0、出勤保留、团队和其他球员结果不变。
- [ ] 测试重新打开、恢复积分并再次入库，验证恢复 5 分且无重复事件。
- [ ] 失败路径至少覆盖：身份未确认时阻止提交、旧确认凭证失效、乌龙携带助攻、保存失败不破坏原正式数据。
- [ ] 测试在 CI 通过，独立创建并清理隔离数据，可重复运行，不连接业务数据库。

## 4. 功能需求

- FR-1：系统必须将未成功匹配的分队名字列入试训待确认区域。
- FR-2：系统必须提供将待确认身份重新匹配为正式球员的操作。
- FR-3：系统必须阻止含未处理身份的比赛确认入库。
- FR-4：系统必须允许按比赛日手工登记试训名字。
- FR-5：系统必须按事件节次展示试训人员的进球、助攻和乌龙记录。
- FR-6：系统必须为试训事件保存明确的本节得分队。
- FR-7：系统必须依据包含试训事件的实际比分计算团队结果。
- FR-8：系统必须排除试训人员的正式赛季个人统计。
- FR-9：系统必须正常统计与试训人员配合的正式球员进球或助攻。
- FR-10：系统必须提供独立乌龙球录入区域。
- FR-11：系统必须拒绝带助攻的乌龙事件。
- FR-12：系统必须把乌龙计入受益队比分。
- FR-13：系统必须为正式球员单独汇总队内乌龙球数。
- FR-14：系统必须在比赛展示中将乌龙与普通进球分列。
- FR-15：系统必须提供按比赛日取消正式球员个人积分的操作。
- FR-16：系统必须将被取消计分球员该日基础积分归零。
- FR-17：系统必须使被取消计分球员该日全部额外积分不生效。
- FR-18：系统必须保留被取消计分球员原本的出勤计算规则。
- FR-19：系统必须允许恢复该日积分资格并重新计算积分。
- FR-20：系统必须持久保存人工确认的试训身份和积分资格。
- FR-21：系统必须在相关内容改变后使旧确认凭证失效。
- FR-22：系统必须在重新确认时事务性替换旧正式结果。
- FR-23：系统必须保持历史比赛默认积分资格为正常计分。

## 5. 非目标

- 不建立试训人员跨赛季档案、试训排名或转正审批流程。
- 不按缺席小节、上场时间或替补次数折算个人积分。
- 不要求管理员维护逐节完整出场阵容或一对一替补关系。
- 不新增缺席考勤处罚规则，不自动取消迟到／受伤者积分。
- 不给乌龙附加扣分规则，不建立乌龙榜。
- 不扩展队外赛试训和代打规则，不推断未标记的历史乌龙。
- 不重做现有团队排名及同分人工确认算法。

## 6. 界面设计考虑

- 分队录入页在红、蓝、白队名单之外增加试训区域；无法识别的名字保留原文并突出待确认状态。
- 比赛确认页使用“试训球员”“普通进球”“乌龙球”分区，避免所有事件堆叠在一个表格。
- 试训区域业务列严格遵循用户要求：姓名、进球节次、助攻节次、乌龙节次。身份纠正等按钮作为操作项。
- 试训人员在事件球员选择器中带“试训”标记，与正式球员区分；不为其选择固定原队。
- 计分资格操作靠近当天正式球员名单，标记后直接显示状态；提示“本场所有个人积分为 0，出勤与比赛事件保留”。
- 单个事件只编辑一次；试训区核对信息、乌龙个人数据均从事件生成，避免重复录入。
- 移动端可横向滚动事件表，关键确认按钮保持可见；桌面与移动端均须浏览器验收。

## 7. 技术约束与集成点

- 当前 GoalEvent.scorerId 必须关联 Player；需要扩展参与者身份表达，以独立试训记录引用事件，不能创建虚构正式 Player 充当占位。
- 普通／乌龙事件仍使用统一可重算的数据来源；界面分区不意味着维护两套重复比分。
- 保持正式球员同一比赛日仅一条 TeamAssignment 的约束；代打不改变当天原队。
- 积分资格应属于“比赛日 + 正式球员”，不能使用 Player 全局标记影响其他比赛。
- 统一更新分队解析、AI schema、规则解析、确认请求校验、确认事务、统计读取及展示类型。
- 身份和积分资格必须纳入确认内容校验，沿用 lib/match-events.ts 与 lib/server/event-confirmation.ts 的确认机制。
- 统计规则继续集中在 lib/stats/calculate.ts；同时覆盖手工 bonus、文本 bonus、奖项积分等入口，防止绕过资格判断。
- 比赛分享／导出与个人记录使用同一分类口径；公开接口仅暴露所需事件信息，不暴露管理员或确认凭证。
- 数据库迁移保留既有事件和原有积分资格；历史明确乌龙使用事件重算，无须复制为新事件。
- 现有资料 tasks/prd-internal-match-event-exceptions.md 作为前序需求；本 PRD 对“手动取消积分资格”和“个人乌龙数”的规定优先，未修改部分沿用。

## 8. 成功指标

- 核心统计测试、类型检查、生产构建与新增自动化端到端测试通过；桌面及移动端完成浏览器验收。
